# ADR-0036 — Настройка AI через административный интерфейс

- Статус: Superseded частично: расположение UI и маршрут страницы — [ADR-0037](ADR-0037-ai-settings-tab.md); остальные решения действуют.
- Дата: 2026-10-21
- Задача: FLQ-11
- Частично заменяет [ADR-0003](ADR-0003-llm-provider-openai-compatible.md): источник конфигурации, хранение ключа и семантику env kill-switch.
- Уточняет decision log §10.3 и Admin Operations из architecture overview §7.9.
- Связан с ADR-0008 (авторизация), ADR-0034 и ADR-0035 (поставка).
- Реализовано в FLQ-11; автоматическая и браузерная приёмка, включая HTTPS и девять языков UI, завершена. Публикация релиза выполняется отдельно.

## Контекст

FLQ-50 обеспечивает установку готового приложения и создание администратора.
Следующий шаг пользователя — подключить AI — пока требует редактирования окружения
и перезапуска API/worker. Первоначальная FLQ-11 предлагала только read-only
просмотр провайдера, runtime kill-switch, список пользователей и метрики.
Такой состав не завершает простой сценарий первого запуска.

Пользователь согласовал первую версию админки только для настройки AI:
«установил → вошёл → подключил модель → проверил → пользуешься».
Это явное расширение первоначального решения о конфигурации через env.
Остальные административные возможности отложены.

## Решение

### 1. Сценарий и границы

Администратору доступен раздел `/admin/ai` с видимым входом из интерфейса;
`/admin` ведёт в этот раздел. Создание первого администратора остаётся частью
установки. Страница не требует настроенного AI, установленного словаря или
изменения `.env`. Настройку можно пропустить: продукт сохраняет режим без AI.

Один активный OpenAI-compatible Chat Completions endpoint и одна модель действуют
на весь инстанс: переводы, AI-чат и существующие AI-функции тренажёра.
Локальные серверы используют тот же контракт. Glosano подключается к уже
работающему серверу; не устанавливает runtime и не скачивает модели.

Поля и действия первой версии:

| Поле / действие | Контракт |
| --- | --- |
| Включить AI | Постоянная настройка инстанса; выключение не удаляет подключение |
| Пресет | OpenAI, OpenRouter, Ollama, LM Studio, другой OpenAI-compatible сервер; только помощь в заполнении, без отдельных адаптеров |
| Адрес сервера | Редактируемый base URL; серверная валидация, подсказка об адресе, доступном из Docker |
| API-ключ | Ввод, замена и явное удаление; для серверов без авторизации допускается отсутствие ключа |
| Модель | Ручной ввод идентификатора обязателен как доступный путь; загрузка списка — дополнительное явное действие, если endpoint поддерживает `/models` |
| Проверить подключение | Короткий запрос к выбранной модели с фиксированным диагностическим текстом, без пользовательских материалов |
| Сохранить | Атомарное сохранение, результат виден сразу; новые запросы используют настройки без перезапуска |

Отсутствие `/models` не блокирует ручной ввод. Доступность списка моделей сама
по себе не считается успешной проверкой Chat Completions. Проверка может быть
платной: это кратко обозначается рядом с действием. Ошибки различают недоступный
сервер, timeout, авторизацию, неизвестную модель, ограничение провайдера и
несовместимый ответ; сырой ответ провайдера и секреты не показываются.

Открытие формы, выбор пресета и сохранение не выполняют внешних запросов.
Проверка и загрузка моделей работают с черновиком, не меняя активное подключение.
Они доступны по явному действию администратора и при обычном AI-off, чтобы можно
было проверить подключение до включения AI для пользователей. Это единственное
исключение для диагностики; `GLOSANO_LLM_FORCE_DISABLED` запрещает и эти вызовы.
Неуспешная проверка сохраняет введённые поля; валидную конфигурацию можно сохранить
и при временно недоступном провайдере. Включение требует непустых адреса и модели.
Устаревший результат проверки после изменения полей не отображается как актуальный.

### 2. Постоянные настройки и совместимость с env

PostgreSQL — источник правды после первого явного сохранения через админку.
Хранится одна конфигурация инстанса: enabled, base URL, model, зашифрованный ключ
или его явное отсутствие, revision, время и автор изменения. Сохранение использует
проверку revision: конкурентное редактирование не затирает изменения молча.
Redis не является единственным хранилищем настроек или выключателя.

Приоритет определяется однозначно:

1. Новый `GLOSANO_LLM_FORCE_DISABLED=true` запрещает **все** исходящие AI-вызовы,
   включая проверку подключения и загрузку моделей. Default — `false`.
   Интерфейс показывает причину блокировки и не может её снять.
2. Если конфигурация сохранена в БД, используются все её поля. Не происходит
   смешивания с прежним env-ключом, адресом или моделью; удалённый ключ не появляется
   снова из окружения.
3. Если конфигурации в БД нет, сохраняется прежнее поведение `GLOSANO_LLM_ENABLED`,
   `GLOSANO_LLM_BASE_URL`, `GLOSANO_LLM_API_KEY`, `GLOSANO_LLM_MODEL`.
   Интерфейс показывает источник «Окружение» и позволяет явно перейти на настройки
   приложения. Открытие страницы или миграция сами по себе такой переход не делают.

На чистой установке AI выключен, но администратор может включить его через UI,
не меняя установленное по умолчанию `GLOSANO_LLM_ENABLED=false`. После сохранения
это legacy-значение уже не является аварийным запретом: для запрета используется
`GLOSANO_LLM_FORCE_DISABLED`. Это намеренное изменение ADR-0003, которое должно
быть явно описано в upgrade/self-hosting/Portainer документации.

При первом сохранении администратор может сохранить существующий env-ключ
серверным действием, не получая его в браузер. Смена адреса/пресета требует явного
ввода ключа для нового подключения либо выбора «без ключа»: старый секрет не
переносится автоматически на другой сервер, в том числе при диагностике.

Force-disabled передаётся одинаково в API и worker всеми поддерживаемыми
Compose-вариантами. Изменение env требует штатного пересоздания обоих сервисов;
обычное выключение через админку применяется без него. Редактирование `.env`
из веб-приложения и доступ к Docker socket не нужны.

### 3. Секреты и права доступа

Настройки, сохранение, проверка и список моделей доступны только `role=admin`.
Сервер проверяет сессию и роль независимо от скрытого пункта меню; для действий
применяется существующая CSRF-защита. Learner не получает адрес провайдера или ключ;
ему доступен только необходимый признак доступности AI.

Ключ хранится в БД с аутентифицированным шифрованием через поддерживаемую
криптографическую библиотеку. Ключ шифрования выводится из существующего
`GLOSANO_SECRET_KEY` с отдельным контекстом назначения; криптографические примитивы
не реализуются самостоятельно. Установщики уже генерируют случайный секрет и
передают его API/worker: нового ручного шага для чистой установки не появляется.
Сохранение ключа с известным default/непригодным секретом инстанса отклоняется.

GET настроек возвращает только признак наличия ключа. Отсутствие нового значения
означает «сохранить существующий», удаление — отдельное явное действие.
Ключ не попадает в логи, ответы ошибок, localStorage, задания очереди или личный
JSON-экспорт. Изменение настроек журналируется только метаданными.

Резервная копия БД содержит ciphertext; для восстановления нужен исходный секрет
инстанса, хранимый отдельно от БД. При его утрате/смене AI не использует старый env
как скрытый fallback: показывается состояние «нужно повторно ввести ключ», базовый
продукт работает. Процедура смены секрета описывает повторный ввод провайдерского
ключа; автоматическая ротация с перешифрованием и её UI отложены.

Исходящие запросы выполняет backend, включая диагностику. Частные адреса допустимы
для локальных серверов, HTTP — для локальной доверенной сети; облачное подключение
использует HTTPS. URL с credentials, неподдерживаемой схемой или адресом metadata
службы отклоняется; автоматические redirects не пересылают секреты. Проверки
ограничены по времени и размеру ответа. Универсальный HTTP-proxy не создаётся.

### 4. Применение в API и worker

Все AI-точки используют общий механизм получения эффективной конфигурации.
Перед новым внешним вызовом, включая повторную попытку и выполнение отложенного
задания, проверяются актуальные настройки и выключатели. Недоступность хранилища
или ошибка расшифровки запрещает AI-вызов, а не возвращает процесс к старому env.

После успешного сохранения новые операции используют новую revision в API и
worker. В рамках одной операции адрес, ключ и модель берутся из одного снимка;
изменение подключения между попытками завершает операцию контролируемой ошибкой,
не отправляя её незаметно другому провайдеру. Уже отправленный запрос нельзя
«отозвать» у провайдера: выключение запрещает следующие вызовы и повторы, а
получаемый поток прекращается по существующему механизму отмены, где он применим.

Выключение не удаляет историю чата, сохранённые переводы и пользовательские данные.
UI обновляет доступность AI без повторного входа. Смена подключения не переписывает
сохранённые пользовательские переводы; автоматический AI-кэш учитывает revision
подключения и остаётся изолированным по пользователям.

### 5. Что отложено

Список и управление пользователями/ролями, переключение публичной регистрации,
словари, OCR, системные метрики и ошибки, очереди, backup UI, квоты и usage,
retention UI, редактирование prompts, несколько активных провайдеров, routing,
разные модели по сценариям и персональные ключи не входят в FLQ-11.
Timeout и существующие технические лимиты остаются в env. Общий экран аудита
и управление загрузкой локальных моделей также отложены.

## Последствия и проверка

Путь от установки до AI завершается в браузере. Появляются постоянная конфигурация,
защищённое хранение секрета и общий механизм применения настроек; это изменение
backend и frontend, а не только форма поверх текущего Settings.

При реализации проверяются чистая установка и первое сохранение, legacy env и
переход в БД, force-disabled, смена провайдера и отсутствие утечки старого ключа,
конкурентное сохранение, отказ провайдера, отсутствие `/models`, API/worker без
перезапуска, отложенные задания/retry, потеря ключа шифрования и restart/restore.
Для интеграций — настоящие PostgreSQL/Redis и управляемый тестовый провайдер.
Браузерный сценарий проверяется для admin/learner, локальной Docker-поставки и
HTTPS-сервера, включая адаптивную форму и девять языков UI по ADR-0032.

Сохраняются OpenAI-compatible контракт, необязательность AI, per-user privacy,
пометка AI-generated и работоспособность базового продукта без AI. Правила
словарных данных, Token/Phrase, SRS и метрик этим решением не меняются.

## Отклонённые альтернативы

- Только read-only просмотр env: не устраняет ручную настройку после установки.
- Запись в `.env` и перезапуск из UI: зависит от способа поставки и требует
  административного доступа к контейнерам.
- Только Redis override: не даёт надёжного постоянного источника конфигурации.
- Сохранение API-ключа открытым текстом в БД: резервная копия БД раскрывала бы ключ.
- Считать legacy `LLM_ENABLED=false` постоянным запретом поверх UI: на чистой
  установке включить AI из браузера было бы невозможно.
